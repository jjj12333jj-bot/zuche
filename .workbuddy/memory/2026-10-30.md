### 关键决策（重要，可复用）
**车辆可用性统一以 `vehicle.status` 为准，不再反推订单状态。**
原因：seed 里 61 张未结束订单压在 24 台车上（每台 2~6 张），若按订单判占用，
24 台全部「占用中」，改状态/调车功能直接不可用。
所以 `occupied == (status == 2)`，且车辆列表的「当前订单」字段用
`CASE WHEN v.status = 2 THEN (子查询) END`，避免「可租 + 在租」同屏矛盾。
代价：与订单状态不完全自洽，已写入 docs/06 第 7 节局限。

**调车方向 = 调出方发起、平台审批。** 前端不传 fromStoreId，服务端按车辆归属推导；
审批通过用 CAS `UPDATE vehicle SET store_id=? WHERE id=? AND store_id=from AND status=1`，
影响行数 0 即拒绝，整笔事务回滚，申请保持 PENDING。

- 台账只增不改；进场里程 > 当前里程时同步更新车辆档案；REPAIR 且 status=1 自动置 3
- 越权一律 404（不区分「不存在」与「不是你的」，防 ID 枚举）
- 调价允许对已租出车操作（订单已快照单价）
- 状态只允许手工设 0/1/3，2 由支付/归还维护

## S6.5：seed v2 重做 + 恢复「车日利用率」+ 接入 GitHub（19:30~20:45）

### 为什么要重做
v1 的 300 单用 `((i*5 + j*7 + 3) % 24) + 1` 随机挑车，同车在时间轴上大量重叠
（24 台车压着 61 条活跃单），导致：
- 车日利用率算出 563%，S5 只能放弃该指标；
- 网点概览出现「14 单在租 / 0 台已租」这类矛盾组合；
- 订单 store_id 与车辆 store_id 对不上，要靠事后 UPDATE 补。

### 排程算法（sql/02-seed.sql §6）
1. 按状态定用车窗口 `[s_date, e_date)`（完成/取消回溯、在租跨今、逾期计划还车已过、待取车未来）；
2. 在车辆池里挑「该窗口无档期 + 已排单数最少」的车：`NOT EXISTS(tmp_busy)` + `ORDER BY tmp_load.cnt`；
3. 排上后写 `tmp_busy`，取消单不写（立即释放）；
4. **逾期单探闲要探到"今天"**（`pe`/`hold_end`），否则会出现"车还没还又被租出去"；
5. 每个网点至少留 1 台可租（`tmp_store_free` 计数，避免整店 0 台可租）；
6. 订单 store_id 直接取车辆 store_id，省掉事后对齐。

MySQL 坑：
- `lead` 是 8.0 保留字，变量名要改 `lead_days`；
- 同一条语句里两次打开同一张临时表报 ERROR 1137，所以"判闲"用 tmp_busy、"排序"用 tmp_load；
- 循环变量跨轮复用要显式置 NULL（u_id 忘了清空，导致 94% 的订单都排在 user2/user5/user6 上）。

### 数据结果
状态 252 完成 / 24 取消 / 6 在租 / 6 逾期 / 12 待取车；
车辆 24 台 = 9 可租 + 12 已租出 + 2 维保（9、18）+ 1 下架（24）；
6 项一致性自查全 0；车日利用率 7 天 63.3% / 30 天 59.2% / 90 天 56.4%（窗口 48 天）。
逾期归还概率按信用等级分档（WATCH 1/7、NORMAL 1/11、GOOD 1/23、EXCELLENT 1/41），
所以「信用越低逾期率越高」3.8% → 6.8% → 9.4% → 17.6% 是造出来的、不是撞出来的。

### 指标恢复
`KpiVO` / `StoreStatVO` / `StoreOverviewVO` 各加 rentableVehicles / occupiedVehicleDays /

分母 `可租车辆 × 天数`，窗口左端不早于首单日期（否则被"上线前"空档稀释）。
