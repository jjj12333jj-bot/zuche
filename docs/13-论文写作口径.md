## 二、订单状态：8 个，不是 7 个

枚举 `OrderStatus` 实际有 8 个值：

```
WAIT_PAY 待支付 → WAIT_PICKUP 待取车 → IN_USE 在租 → WAIT_RETURN 待归还
→ RETURNED 已归还 → COMPLETED 已完成
分支：CANCELLED 已取消（终态）、OVERDUE 逾期（可回到归还流程）
```

**推荐表述**：

> 订单主流程包含 7 个状态（待支付、待取车、在租、待归还、已归还、已完成、逾期），另有“已取消”作为终止分支，共 8 个状态值。状态流转由 `OrderStatus` 枚举与 `OrderStateMachine` 统一约束，非法流转直接返回业务异常。

不要写成“七状态机”而不解释——枚举里就是 8 个，被追问会答不上来。

**两个自动触发**（可写进状态机小节）：

- 每日 01:00 逾期扫描：超期未还订单置 `OVERDUE`，按天扣分
- 每日 01:30 超时取车扫描：超过取车日 N 天（默认 1 天）未取车的 `WAIT_PICKUP` 订单自动取消，退款、释放车辆、按“支付后取消”扣 3 分

## 三、信用与押金（创新点 1、2 的写作口径）

**押金浮动**：押金 = 标准押金 × 信用系数，四档 0.8 / 0.9 / 1.0 / 1.2，后台可改。
**快照机制**：下单时把 `credit_score_snapshot`、`credit_level_snapshot`、`deposit_coefficient` 写入订单，后续调整规则不影响在途订单。

**可直接抄的一段**：

> 押金不再是一个固定值，而是由下单时刻的信用等级决定：优秀档 8 折、良好档 9 折、一般档原价、待观察档上浮 20%。为避免“后台调规则把在途订单的账改乱”，下单时把信用分、等级与押金系数一并快照进订单，规则调整只对之后的新订单生效。

**评分—定价—准入闭环**：

> 信用分由订单事件驱动（完成 +2、按时归还 +5、逾期 −3/天、逾期归还 −5、支付后取消 −3），扣分可通过申诉复核补回；分数同时决定押金系数与下单准入，风控名单分预警、限制下单、黑名单三级，在下单校验时实时生效。

**实测数字可引用**：同一台宝马 5 系（标准押金 6000），优秀档用户实付 4800，一般档用户实付 6000；黑名单用户下单被直接拒绝。

**代码里没有实现**，只有首页一个静态“租车 Q&A”常量文案。写作时必须用“规划 / 设计”口径，不能用“已实现”。

**可直接抄的一段**：

> 第三项创新是把业务规则做成可解释的问答入口：以押金、逾期、退改规则表与订单快照为依据生成答案，用户询问“为什么这单押金是 1.2 倍”“逾期怎么计算”时，答案可回溯到具体规则条款；无法回答的问题转人工并留下会话记录，降低中小商户的客服成本。该模块规则梳理与接口设计已完成，作为下一阶段实现内容。

**答辩口径**：被问“做了吗”，答“排在其他模块完善之后，规则梳理已完成”，不要说“已经做了”。

## 五、六项一致性自检（论文“测试”章节直接用）

以 `sql/02-seed.sql` 第 11.1 节为准，六条 SQL 覆盖六类自相矛盾：

| # | 检查项 | 判定逻辑 |
|---|---|---|
| 1 | 同车档期重叠 | 同一车辆两笔未取消订单的租期区间相交（逾期单按“占用到今天”计算） |
| 2 | 订单状态与日期矛盾 | 已完成却未到结束日、在租但日期不覆盖今天、待取车却已过期等 |
| 3 | 车辆状态与在租订单不符 | 标记已租出却无在途订单，或反之 |
| 4 | 订单金额与明细不符 | 订单租金 ≠ 明细租金之和 |
| 5 | 订单网点与车辆网点不符 | 订单取车网点 ≠ 车辆所属网点 |
| 6 | 信用分与日志不闭合 | `credit_score ≠ clamp(100 + Σscore_change, 0, 150)` |

**推荐表述**：

> 数据一致性不靠人工抽查，而是固化为 6 条可重复执行的 SQL：覆盖档期、订单状态、车辆状态、金额明细、网点归属与信用分闭合。种子数据灌入时自动执行，六项异常数均为 0；换机器、重新灌库后重跑结果一致，结论可复现。

> 注意：`docs/04-S5验证手册.md` 附录里另有一组“六项”（零变动日志、应付实收等），属于 S5 阶段的管理端抽查口径，**不要与上面六条混用**。

## 七、答辩演示可当场验证的三件事

1. **押金差异**：`user1`（137 分，优秀）与 `user3`（84 分，一般）试算同一台宝马，押金 4800 vs 6000
2. **名单拦截**：`user3` 在风控名单中，下单被拒，提示“已被列入风控名单”
3. **订单闭环**：下单 → 支付 → 网点交付 → 申请归还 → 确认归还 → 押金退还，信用 +2 与 +5 落库
