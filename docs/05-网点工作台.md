## 一、为什么做这一块

S5 做完后，系统三角色中：

| 角色 | 状态 |
|---|---|
| `USER` | 完整：浏览 → 下单 → 支付 → 取车 → 归还 → 信用中心 → 申诉 |
| `SYS_ADMIN` | 完整：运营看板 + 信用规则/用户/申诉/风控名单 |
| `STORE_ADMIN` | **空壳**：能登录、能看到菜单，点进去全是「模块建设中」 |

`store` 模块当时只有 `entity` 和 `mapper`，没有任何 Controller。
这是 RBAC 完整性的硬伤——答辩时「你的三角色分别能做什么」答不完整。

本轮把它补上。

## 三、关键设计

### 3.1 归属隔离：靠 `store_id`，不靠前端

`JwtInterceptor` 解析 token 时把 `storeId` 写进了 `LoginUser`，
所以每个请求天然知道「我是哪个网点的」。

```java
private LeaseOrder requireStoreOrderForUpdate(Long orderId) {
    Long storeId = requireStoreId();          // 非网点管理员直接 403
    LeaseOrder order = orderMapper.selectByIdForUpdate(orderId);
    if (order == null || !storeId.equals(order.getStoreId())) {
        throw new BusinessException(ResultCode.NOT_FOUND, "本网点不存在该订单");
    }
    return order;
}
```

**为什么返回 404 而不是 403**：告诉调用方「这个订单不在你的管辖范围」就够了，
不暴露「订单确实存在、只是不归你」，避免被用来探测他人订单号。

查询侧同理：`selectStoreOrderPage` 的 SQL 里写死了 `o.store_id = #{storeId}`，
不是查出来再过滤，越权数据根本不会从数据库出来。

### 3.2 结算逻辑只有一份

用户端和网点端都能「确认归还」，但结算（违约金、押金退款、信用分）**只有一套实现**：

```java
public OrderReturnVO confirmReturn(Long orderId) {          // 用户端
    return doConfirmReturn(requireOwnOrderForUpdate(orderId));
}

public OrderReturnVO confirmReturnByStore(Long orderId) {   // 网点端
    return doConfirmReturn(requireStoreOrderForUpdate(orderId));
}

private OrderReturnVO doConfirmReturn(LeaseOrder order) { /* 唯一实现 */ }
```

差别只在归属校验（`user_id` vs `store_id`），主体逻辑完全共用。
如果两个入口各写一套，违约金一定会算出两个数。

### 3.3 网点订单多三个客户字段

`StoreOrderVO extends OrderListVO`，补 `customerName / customerPhone / customerUsername`。
网点员工要能一眼看出「这台车是谁租的、电话多少」，否则没法联系客户催还。
用户端不需要（本来就是自己的单），所以不放在父类上。

## 四、顺带修掉的数据问题

做网点概览时发现「15 单在租，0 台车已租」这种同屏矛盾，查下去是**种子数据缺陷**：

```
订单的 store_id（取车网点）与车辆实际的 store_id 完全无关
300 单全部不一致，其中 100 单是多车订单且车辆跨网点
```

代码是对的——`buildQuote` 里 `vo.setStoreId(vehicle.getStoreId())`，
下单时订单网点直接取车辆所属网点。问题只在 seed 生成数据时没遵守这个约束。

**已修复**：把 300 单的 `store_id` 对齐到「第一台明细车辆」的网点，修复后 7 项一致性检查全 0。

```sql
UPDATE lease_order o
JOIN (SELECT oi.order_id, MIN(oi.id) AS first_item FROM order_item oi GROUP BY oi.order_id) f
  ON f.order_id = o.id
JOIN order_item i ON i.id = f.first_item
JOIN vehicle v ON v.id = i.vehicle_id
SET o.store_id = v.store_id
WHERE o.deleted = 0 AND o.store_id <> v.store_id;
```

备份表：`_bak_order_store`（309 行）、`_bak_vehicle_status`（24 行），需要回滚时：

```sql
UPDATE lease_order o JOIN _bak_order_store b ON b.id = o.id SET o.store_id = b.store_id;
```

## 六、已知局限（如实记录）

### 6.1 同车多单（已在 seed v2 修复）

**历史问题**：v1 的种子数据里每台车被 2~6 个未结束订单同时占用（时间重叠），
网点概览会出现「14 单在租、0 台已租」这种刺眼组合，车日利用率也算出了 563%。

**根因**：seed 生成订单时用 `((i*5 + j*7 + 3) % 24) + 1` 随机挑车，
没有做「同一时间段一台车只能被一单占用」的约束。

**v2 的修法**（`sql/02-seed.sql` §6）：订单按**车辆档期**排程——
先按状态定用车窗口，再在车辆池里挑一台该窗口内没有档期的车（已占用天数最少者优先），
占上后写入临时档期表，后续订单不会再撞车；逾期单按"占用到今天"处理，
取消单立即释放车辆。生成结束后由 §6.1 把有进行中订单的车统一置为 `status=2`。

**结果**：同车档期重叠 0 条；在租车辆 12 台 ↔ 活跃订单 12 单一一对应；
车日利用率落在 56%~63%（随窗口变化），`occupied == (status == 2)` 恒等成立。

> 这条记录保留下来是因为它值得写进论文的"数据构造"一节：
> 统计口径的可信度，最终取决于数据本身有没有违反业务约束。

### 6.2 实退 0 元不生成退款流水

当违约金 ≥ 押金时，实退 0，`RefundService.refund()` 直接跳过不写流水
（代码注释里写明这是有意设计，零押金订单同理）。

代价是：订单详情里看不到「押金被全额抵扣」的书面说明，只有一个
`deposit_refund_status = REFUNDED`。后续可在订单详情的退款区块补一条提示文案。

### 6.3 admin 访问网点接口返回 403

`@RequireRole(STORE_ADMIN)` 是精确匹配，`SYS_ADMIN` 不在其中。
这是有意的职责划分：管理员的全局视图在 S5 看板，网点工作台是操作台。

若答辩需要「管理员也能看网点数据」，把注解改成多角色即可，改动量很小。
