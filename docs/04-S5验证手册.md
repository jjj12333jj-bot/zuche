### 0.4 关于数字

下文所有具体金额、单量都是**上面那个快照时刻**的真实值。看板是实时聚合的，
你在这期间下过单、退过款、结算过违约金，数字就会变。

更要紧的是：**统计窗口按当天日期滚动**。`days=30` 指「含今天在内的最近 30 天」，
所以每过一天，窗口左边界就右移一天——订单量和区间营收都会跟着变（累计营收不变）。

判断标准：
- **结构类预期**（区块有没有、文案对不对、图表画不画得出来）→ 必须完全一致。
- **数值类预期**（具体金额）→ 允许变化，但必须满足第 4、5 步的 SQL 关系式。
  这两步的 SQL 已经用 `CURDATE()` 动态取窗口起点，**任何一天跑都能对上**，
  这是判断数据对不对的最终依据，不要拿本文的数字硬套。

**三个必须成立的规律**：

1. **累计净营收不随窗口变化**（三列都是 ¥185,541.35）——它是累计口径；变的只是卡片脚注里的区间营收。
2. **近 90 天区间营收 = 累计净营收**（都是 ¥185,541.35）——因为所有支付都发生在近 90 天内，窗口覆盖了全集。这条对上了，说明区间口径没算错。
3. **窗口越大，完成率越高**（30.8% → 79.1% → 84.0%）——近 7 天里新下的单还没走到归还，属于正常现象，也说明完成率不能跨窗口直接比较。
4. **窗口越大，车日利用率越低**（63.3% → 59.2% → 56.4%）——近 7 天正好压着一批在租/逾期单，越往前翻历史空档越多。
   90 天窗口的"近 N 天"显示 48，因为平台数据只覆盖 48 天，分母不会被拉到 90 天。

## 第 4 步：净营收对账（最硬的一步）

### 4.1 先在页面上记下一个数（近 30 天）

- 「累计净营收」卡片脚注里的区间营收：**¥112,988.31**

### 4.2 再用 SQL 拆开算

> 窗口起点用 `DATE_SUB(CURDATE(), INTERVAL 29 DAY)` 现场算，不要手写日期。
> 手写的话，隔一天就跑出「差一天的窗口」，对不上是正常的，会被误判成 bug。

```sql
-- 含今天在内的 30 天窗口：今天往前 29 天（与后端 LocalDate.now().minusDays(d-1) 完全一致）
SET @s = DATE_SUB(CURDATE(), INTERVAL 29 DAY);
SELECT @s AS window_start, CURDATE() AS window_end;

SELECT
  (SELECT COALESCE(SUM(amount),0) FROM payment_record
    WHERE status='SUCCESS' AND pay_type='RENT' AND pay_time >= @s)  AS rent_in,
  (SELECT COALESCE(SUM(amount),0) FROM refund_record
    WHERE status='REFUNDED' AND refund_type='CANCEL' AND refund_time >= @s) AS rent_refund,
  (SELECT COALESCE(SUM(late_fee),0) FROM lease_order
    WHERE deleted=0 AND late_fee > 0 AND return_time >= @s)          AS late_fee,
  (SELECT COALESCE(SUM(amount),0) FROM payment_record
    WHERE status='SUCCESS' AND pay_type='RENT' AND pay_time >= @s)
  - (SELECT COALESCE(SUM(amount),0) FROM refund_record
    WHERE status='REFUNDED' AND refund_type='CANCEL' AND refund_time >= @s)
  + (SELECT COALESCE(SUM(late_fee),0) FROM lease_order
    WHERE deleted=0 AND late_fee > 0 AND return_time >= @s)          AS net_revenue;
```

**快照结果（10-30 18:22，窗口 10-01 ~ 10-30）**

| window_start | window_end | rent_in | rent_refund | late_fee | net_revenue |
|---|---|---|---|---|---|
| 2026-10-01 | 2026-10-30 | 112,427.78 | 4,948.19 | 5,508.72 | **112,988.31** |

`112,427.78 − 4,948.19 + 5,508.72 = 112,988.31`，与页面脚注**分毫不差**。

### 4.3 这条对账说明了什么（答辩可直接背）

- 营收只认 `payment_record.pay_type='RENT'` 的**成功**流水，不是拿订单表 `rent_amount` 加总。
  订单应付 ≠ 实收（有取消、有退款），用订单表算会把没收到钱的单也算成收入。
- 退款只认 `refund_type='CANCEL'` 且状态 `REFUNDED` 的，押金退款不进营收。
- 违约金只算 `late_fee > 0` 且已归还（`return_time` 非空）的单，没收到的预估违约金不算。
- 押金（`pay_type='DEPOSIT'`）全程不参与营收计算——它是代收代退，不是收入。

> 顺便验了个隐性正确性：`late_fee` 合计 1,600 来自两单——订单 298（逾期 5 天，1,000 元）和
> 订单 318（逾期 3 天，600 元），都是已归还状态。未归还订单的违约金是**预估展示**，不进这个数。

## 第 5 步：漏斗与订单表对账

```sql
SET @s = DATE_SUB(CURDATE(), INTERVAL 29 DAY);   -- 与第 4 步同一个窗口

SELECT COUNT(*)                        AS order_total,
       SUM(pay_time    IS NOT NULL)    AS paid,
       SUM(pickup_time IS NOT NULL)    AS picked,
       SUM(return_time IS NOT NULL)    AS returned,
       SUM(status='COMPLETED')         AS completed,
       SUM(COALESCE(overdue_days,0)>0) AS overdue
FROM lease_order
WHERE deleted=0 AND create_time >= @s;
```

**快照结果（10-30 18:22）**

| order_total | paid | picked | returned | completed | overdue |
|---|---|---|---|---|---|
| 177 | 166 | 152 | 140 | 140 | 15 |

逐列对上页面：漏斗 177 / 166 / 152 / 140 / 140，指标卡「逾期订单 15」。

**这一条证明漏斗不是用 status 反推的**：五级全部取自订单自己的时间戳
（`pay_time` / `pickup_time` / `return_time` / `status`）。
好处是「取过车后来又取消」的历史动作不会从漏斗里凭空消失，台阶是真实的业务动作序列。

> 想现场验证这点：找一单 `status='CANCELLED'` 但 `pickup_time` 不为空的历史订单，
> 它在「取车」这一级被计入，在「完成」这一级没被计入——这正是我们希望的行为。

## 第 6 步：边界与异常（接口层，答辩加分）

以下命令在 Git Bash / PowerShell 里都能跑。`<TOKEN>` 换成 admin 登录返回的 token。

### 6.1 拿 token

```bash
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}'
```

返回体里 `data.token` 就是。

### 6.2 权限矩阵（后端真的在拦，不只是前端藏菜单）

```bash
# 不带头 → 401
curl -o /dev/null -w "%{http_code}\n" \
  "http://localhost:8080/api/admin/dashboard/overview?days=30"

# store1 的 token → 403
# user1 的 token  → 403
# admin 的 token  → 200
```

**快照结果**：`401 / 200 / 403 / 403`

> 注意：本项目 HTTP 状态码恒为 200，真正的业务码在响应体的 `code` 字段里。
> 401/403 是安全拦截器直接写回的 HTTP 状态，属于例外；业务异常（如参数错）是 HTTP 200 + `code=400`。
> 前端 axios 拦截器看的是 `code`，不是 HTTP status。

### 6.3 days 参数边界

```bash
# 999 → 被钳到上限 180，趋势图 180 个点
# 0   → 回落默认 30
# -5  → 回落默认 30
# 空  → 回落默认 30
# abc → 400 参数 days 格式不正确，应为数字
curl -H "Authorization: Bearer <TOKEN>" \
  "http://localhost:8080/api/admin/dashboard/overview?days=abc"
```

**快照结果**

| 入参 | 结果 |
|---|---|
| `days=999` | `days=180`，orderTotal=309，趋势 180 点 |
| `days=0` | `days=30`，orderTotal=300 |
| `days=-5` | `days=30`，orderTotal=300 |
| `days=`（空） | `days=30`，orderTotal=300 |
| `days=abc` | `code=400`，`参数 days 格式不正确，应为数字` |

> `days=abc` 这条是本次验证时发现并修掉的：修之前它落到兜底异常，弹「系统繁忙，请稍后再试」，
> 让人以为服务挂了，实际只是参数写错。现在归到 400，并明确指出是哪个参数。

### 6.4 不存在的路径

```bash
curl -H "Authorization: Bearer <TOKEN>" \
```

### 数据版本说明（seed v2）

S5 第一次验收（10-30 18:22）用的是 seed v1，历史订单由伪随机数直接挑车，
同一台车在时间轴上会撞单，导致「车日利用率」算到 563%，只能放弃该指标。

本次 seed v2 把订单改成**按车辆档期排程**：先定用车窗口，再在车辆池里挑一台
该窗口内没有档期的车，占上档期后写进临时表，后续订单不会再撞车；
逾期单按"占用到今天"处理，取消单立即释放车辆。

结果：

| 检查项 | v1 | v2 |
|---|---|---|
| 同车档期重叠 | 大量（24 台车被 61 条活跃单压住） | **0** |
| 车日利用率 | 563%（不可用） | **56.4% ~ 63.3%**（随窗口变化） |
| 在租车辆 / 活跃订单 | 24 / 61（对不上） | **12 / 12**（一一对应） |
| 订单网点与车辆网点一致 | 需事后 UPDATE 对齐 | 建单时即一致 |

v1 的历史数字（净营收 285,279.23、漏斗 291/261/241/197/197）与 v2 不可比，
以本文档当前数字为准；第 4、5 步的 SQL 用 `CURDATE()` 现场取窗口，
