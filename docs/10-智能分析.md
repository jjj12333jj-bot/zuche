## 2. 四个设计决策

### 2.1 热力图用「下单时间」，不用「取车时间」

第一反应是画「取车时段热力」，因为那才是网点最关心的（要安排交付人手）。
但实际取数后发现了问题：

```sql
SELECT HOUR(pickup_time), COUNT(*) FROM lease_order GROUP BY 1 ORDER BY 2 DESC;
-- 9 点：264 条，其余小时：0 条
```

种子数据里取车时间统一按取车日 `09:xx` 生成，画出来只有一条竖线，
**看起来像图表坏了**。而且真实业务里取车时间本来就是网点指定的，分布会被人为压平。

改用 `create_time`（下单时间）之后，数据里出现了清晰的双峰：

```
09-12 点：47 / 45 / 47 / 45   ← 上午决定行程
18-21 点：33 / 15 / 27 / 18   ← 晚上刷手机下单
13-17 点：几乎为 0            ← 上班时间没人租车
```

这个形态是可以拿去做运营动作的：推送放早上 9 点前和晚上 7 点前，客服排班按双峰来。

### 2.2 车型偏好用气泡，不用排行榜

原来的看板已经有「车型营收 TOP8」横向条形图，那个只能看一个维度。
「偏好」至少是三个维度的事：

| 维度 | 含义 | 视觉映射 |
|---|---|---|
| 订单量 | 用户愿不愿意选 | 横轴 |
| 客单价 | 愿意付多少钱 | 纵轴 |
| 营收 | 最终贡献多少 | 气泡面积 |

结果直接分出了两个阵营：

- **新能源**：98 单（33.6%）、客单 ¥701 → 走量，营收占比 35.5%
- **豪华型**：39 单（13.4%）、客单 ¥1,533 → 单少但营收占比 30.9%

气泡面积用**开方缩放**（`18 + sqrt(rent/maxRent) * 34`），否则一个 6.8 万的营收
会把 1.3 万的压成一个点，视觉上等于没画。

### 2.3 预测用季节性朴素，不用 ARIMA

样本量摆在那里：日粒度只有 45~50 个点。ARIMA 在这个量级上参数估不准，
而且答辩时被问「p、d、q 怎么定的」很难讲圆。

选的是一个三句话能讲完的模型：

```
1. 基准值   = 最近 4 周同一个星期几的平均营收
2. 趋势修正 = 近 7 天均值 ÷ 前 21 天均值（向 1 收缩一半，限幅 0.75~1.35）
3. 区间     = 回测残差标准差 × 1.28（80% 置信），并随步长按 √(1+step/14) 放大
```

三个细节都是为了「不失控」：

- **同星期基准夹逼**：单笔大单（比如租出一台 5 系）会把某个星期四拉高，
  基准值被夹到近期均值的 `0.4~2.0` 倍之间
- **趋势只信一半**：日营收噪声大，完全采信趋势会把预测甩出去
- **区间随步长放大**：预测 14 天比 7 天更不确定，这是常识，也要体现在图上

### 2.4 误差指标选 WAPE，不选 MAPE

这是本次唯一一次「指标口径纠偏」：

```
日粒度 MAPE  = 90.02%   ← 看着像模型废了
周口径 WAPE  = 22.86%   ← 才是真实水平
```

原因是 MAPE 除以实际值：某天只有 1 笔 ¥469 的单，预测 3,400，
这一天的误差就是 625%，直接把平均值拉到 90%。而业务上问的是
**「下周大概能做多少」**，那是合计口径，WAPE（`Σ|误差| ÷ Σ|实际|`）才对。

所以页面上：
- 展示 **周口径 WAPE**（22.9%，标为「中等」可信度）
- 保留 MAE（¥1,737，平均每天差多少）
- MAPE 只在接口里返回，不进页面 —— **不拿会误导的指标充数**

### 2.5 用「区间覆盖率」检验区间是不是吹的

光说「80% 置信区间」没有意义，得验证。回测时统计实际值落在区间内的比例：

```
名义 80%  →  实际 80.95%（21 天回测）
```

说明残差近似正态、区间标定没有虚标。这一条比 R² 更能说服人，
因为 R² 在噪声大的日数据上本来就是负的（本次 -0.248），拿它当卖点会被问穿。

## 3. 关键实现

### 3.1 回测必须「只用当时能看到的数据」

```java
private double predictAt(double[] full, LocalDate firstDate, int origin, int target) {
    double[] hist = Arrays.copyOfRange(full, 0, origin + 1);  // 截断到 origin
    return Math.max(0, weekdayBase(hist, firstDate, target) * trendFactor(hist));
}
```

如果拿全量数据算基准再去比历史，等于**用未来预测过去**，指标会好得离谱。
这里的每一次回测都只喂 `[0, origin]` 这一段。

### 3.2 七步回测算周合计误差

一步回测（预测明天）只能衡量日噪声，业务关心的是周合计：

```java
for (int i = Math.max(14, n - 21); i <= n - 7; i++) {
    double pred7 = 0, actual7 = 0;
    for (int k = 0; k < 7; k++) {
        pred7   += predictAt(series, firstDate, i - 1, i + k);
        actual7 += series[i + k];
    }
    errSum += Math.abs(actual7 - pred7);
    actSum += actual7;
}
wape = errSum / actSum * 100;   // 22.86%
```

### 3.3 SQL 只捞数，不算比率

`GROUP BY WEEKDAY(create_time) + 1` 踩过一次坑：MySQL 8 的
`only_full_group_by` 不认 `SELECT WEEKDAY(x)+1 ... GROUP BY WEEKDAY(x)`，
必须把表达式写成一模一样。`DATE_FORMAT` 与 `DATE()` 混用同理。

## 7. 已知边界

1. **取车时段热力做不了**：种子数据取车时间统一 9:00，要做得先改 seed 的取车时刻分布，
   本轮没动（会牵动订单时间自洽校验）。当前用下单时间替代，业务含义不同但同样可用。
2. **节假日效应没建模**：预测只有「星期因子 + 趋势」，遇到国庆这类长假会低估。
   真实项目应加节假日哑变量或引入外部日历。
3. **预测目标是「支付口径租金」**：按天摊分的权责发生制口径更平滑，
   但与看板的营收口径不一致，本轮没混用。
4. **数据尾部偏薄**：种子数据里最近 3~4 天没有新增的已完成订单（`e_date` 最小取到今天-2），
   所以「近 7 天」合计偏低，预测值相对近期均值为 -12.5% 有一部分是这个原因。
   这一点在页面 tooltip 与本文档里都写清楚，**不假装数据是完美的**。
5. **热力图不支持 14×24 跨周对比**：TASKS 里原本写的「14×24 两种 mode」只做了 7×24，
   跨两周对比需要另一套坐标（周序号 × 小时），当前收益不大。
