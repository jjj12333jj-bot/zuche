# 12 · 评价体系（用户写 / 所有人看 / 网点解释 / 平台管违规）

> 对应页面：用户订单详情「发表评价」、车辆详情「用户评价」、网点端「客户评价」、平台「评价管理」。
>
> 在此之前，评价只有一个后台管理页，12 条评价全部是种子数据——用户下完单、跑完整条流程，
> 无论怎么做都产生不了一条评价。本轮把这个环补上。

---

## 1. 为什么拆成两个维度

原来只有一个 `rating`，用户只能给一个总印象打分。问题是这个分数**没法指导动作**：

- 车旧座椅磨损 → 应该去整备车辆
- 取车排队四十分钟 → 应该去排班加人

一个 4 分把两者搅在一起，运营看完不知道先修车还是先招人。

所以拆成 `vehicle_rating`（车辆状况）与 `store_rating`（门店服务），
`rating` 保留为两者平均，继续给统计、排序、榜单用——**旧口径不变，报表不用改**。

页面上因此能出现这种对比：

```
张**  综合 4 分   车况 ★★★★★ 5.0   服务 ★★☆☆☆ 2.0
      "车很新很好开，但取车排队快四十分钟，店员也没给个说法。"
```

同一台车的聚合也能看出来：车况均分 5.0、服务均分 3.0 —— 问题在门店，不在车。

## 2. 权限边界

这是评价功能最容易做错的地方，也是本轮最核心的设计。

| 角色 | 看 | 回复 | 隐藏 | 删除 |
|---|---|---|---|---|
| 普通用户 | 车辆详情页看脱敏评价 | ✗ | ✗ | ✗ |
| 网点管理员（商家） | 仅本网点 | ✓ 解释性回复 | ✗ | ✗ |
| 系统管理员（平台） | 全平台 | ✓ | ✓ | ✓ |

两条硬规则：

1. **商家不能删差评**。让商家自己删，等于既当运动员又当裁判，评分立刻变成自说自话。
   网点端连删除接口都没有，不是"前端不显示按钮"——`DELETE /api/store/evaluations/{id}` 返回 404。
2. **网点看不到别家**。`storeId` 从 JWT 取，前端传什么都无效；
   跨店回复返回 404 而不是 403，不暴露"这条评价存在、只是不归你"。

删除走逻辑删除（`deleted=1`）而不是 `DELETE`：删了什么、什么原因，事后要能对上账。

## 3. 一单一评怎么保证

三道防线，从软到硬：

1. 前端：订单详情只对 `canEvaluate=true` 显示按钮，评完变成「我的评价」区块
2. 业务层：`countByOrderId(orderId) > 0` 直接拒绝
3. 数据库：`uk_order` 唯一索引，两个标签页同时提交时后到的那条被拦下，业务层翻译成「这笔订单已经评价过了」

**一个容易忽略的点**：`countByOrderId` 不过滤 `deleted`。
违规评价被平台删掉后，唯一索引仍占着 `order_id`，用户再点提交只会撞库报错。
所以"评过没有"必须把已删除的也算上——按钮一开始就不该出现。

## 4. 前台展示的脱敏

车辆详情页是公开接口（`/api/vehicles/**` 在白名单），游客也能看。

`VehicleEvaluationItemVO` 与后台的 `EvaluationVO` **分开定义**，不是同一个类藏几个字段：

- 姓名在 SQL 里就脱敏成「张**」
- 手机号、订单号、网点内部信息**根本不出现在结果集里**

前端"记得别渲染"不算安全措施——少一个字段就少一次泄漏。

## 5. 关键实现

| 位置 | 说明 |
|---|---|
| `EvaluationCreateDTO` | 双维度 1~5 必填，内容 5~500 字；综合分后端算，不接受前端传 |
| `EvaluationService.create()` | 校验归属 → 校验状态 `COMPLETED` → 校验未评价 → 插入 |
| `EvaluationService.vehicleEvaluations()` | 摘要与列表一次返回，前端不用并发两个请求再对齐时机 |
| `EvaluationService.remove()` | 仅管理员，逻辑删除 + `log.warn` 记录原因 |
| `OrderService.fillEvaluationFlags()` | 列表页批量查一次 `IN (orderIds)`，不逐条查库 |
| `OrderEvaluationMapper.selectVehicleEvalPage` | `status=1 AND deleted=0`，姓名脱敏在 SQL 里做 |

## 6. 验证记录

```
POST /api/orders/301/evaluation  {vehicleRating:5, storeRating:2}
  → 200，综合 4（(5+2)/2 四舍五入），标签「满意」
  → 订单详情：canEvaluate=false、evaluated=true
  → 车辆 23 公开接口：车况 5.0 / 服务 3.0，姓名「张**」

重复提交           → 400「这笔订单已经评价过了」
别人的订单 272     → 404「订单不存在」
逾期订单 294       → 400「订单完成后才能评价」
vehicleRating=6    → 400「门店服务评分为 1~5 星」（先命中 storeRating=0）
内容「好」          → 400「评价内容 5~500 字」

网点隔离：store1 见 5 条、store2 见 8 条，8+5=13（12 种子 + 1 新增）
store1 回复 store2 的评价 → 404「本网点不存在该评价」
store2 回复本店评价 → 200，reply 与 replyTime 落库
DELETE /api/store/evaluations/16 → 404 接口不存在，数据 deleted 仍为 0

管理员删除：total 13 → 12，车辆 23 评价 2 → 1 条
订单 301 详情：evaluated 仍为 true（评价被删也不能再评一次）
操作日志：评价管理/删除评价 status=1，客户评价/回复评价 两条
```

## 7. 已知边界

- 评价图片：表里有 `images` 字段、后端会存 JSON 数组、前台会渲染，
  但本轮没做上传入口（种子里的配图仍可预览）
- 没有「用户撤回自己的评价」：`deleted` 只留给平台处置违规用
- 评价不参与信用分计算，也不影响搜索排序（只做展示与统计）
- 车辆详情页评价区按 `create_time DESC` 排，未做「最有帮助」之类的排序
