## 3. 关键设计

### 3.1 车辆可用性只有一个权威字段：`vehicle.status`

全项目对「这台车现在能不能租」的判断统一看 `vehicle.status`：

- 支付成功 → `lockForRent` 置 2（已租出）
- 未支付订单取消 → `releaseRent` 置 1
- 归还完成 → 置 1
- 网点手工可设 0 下架 / 1 可租 / 3 维保中，**2 不可手工设置**

这样做的直接原因是最初的种子数据里存在「可租但仍有历史未结束订单」的情况（每台车被  
2~6 张未结束订单占用，见 `docs/05` 第 6 节）。如果按订单反推占用，24 台车会全部被判为  
「占用中」，网点整店无车可操作，功能直接废掉。

seed v2 已经在数据层面消除了同车重叠（现在在租车辆 12 台 ↔ 活跃订单 12 单，一一对应），  
但**口径不变**：仍然只认 `vehicle.status`，不按订单反推。理由是订单状态机比车辆状态复杂  
（待取车、在租、待归还、逾期都可能"占着车"），把两套状态耦合成一个判断，出问题时  
很难说清是哪边错了。

因此本模块不把订单状态作为阻断条件，只作为**展示信息**：车辆列表里的「当前订单」  
只在 `status = 2` 时回填（`CASE WHEN v.status = 2 THEN ...`），  
避免出现「可租 + 在租」的同屏矛盾。

### 3.2 越权一律 404，不用 403

查询侧 SQL 写死 `v.store_id = #{storeId}`，越权数据不出库；  
写操作侧 `requireOwnVehicleForUpdate` 锁行后校验归属，不匹配返回  
`404 本网点不存在该车辆`。

不区分「不存在」和「不是你的」，是为了不让网点号/车辆 ID 被枚举出来——  
403 等于告诉对方「这条数据存在，只是不归你」。

### 3.3 调车的方向语义是固定的

```
from_store_id ──(车辆当前归属，调出方) ──→ to_store_id（调入方）
        ↑                                        ↑
   申请由调出方发起                    审批通过后归属迁移到这里
```

- **申请权在调出方**：车在谁名下谁提申请，前端不传 `fromStoreId`，  
  服务端按车辆当前归属推导——少一个入参就少一处可被篡改的地方。
- **审批权在平台**（`SYS_ADMIN`）：两个网点私下互相同意就能搬车，等于把资产台账  
  交给一线；而且调车往往伴随运力失衡，平台需要在全局层面拒绝  
  「把车从缺车店调走」这类申请。

状态机：`PENDING → APPROVED / REJECTED / CANCELLED`，终态不可再变。

### 3.4 审批通过是「迁移归属」，不是「改个状态」

```java
// CAS 写法：审批期间车要是被租走或已被别的申请调走，影响行数为 0
UPDATE vehicle SET store_id = #{toStoreId}
 WHERE id = #{vehicleId} AND store_id = #{fromStoreId}
   AND status = 1 AND deleted = 0
```

迁移失败整笔审批回滚，申请保持 `PENDING`，不会出现「申请显示已通过但车没动」。  
实测已验证：把车在审批前 SQL 挪走，审批返回  
`400 该车辆已不在调出网点名下，申请自动失效`，申请状态仍是 `PENDING`。

### 3.5 台账的两个连带动作

| 动作     | 触发条件                             | 为什么                              |
| ------ | -------------------------------- | -------------------------------- |
| 更新车辆里程 | 进场里程 > `current_mileage`         | 台账是里程的唯一可信来源，让人再单独改一次档案迟早会忘；只增不减 |
| 自动置维保中 | 类型 = `REPAIR` 且车辆当前 `status = 1` | 维修中的车还能被下单是真实事故                  |

台账**只增不改不删**：它是资产履历，写错了应该补一条更正记录，不应抹掉历史。

## 4. 业务规则与提示语文案

### 4.1 调价

| 场景          | 返回                                                                                 |
| ----------- | ---------------------------------------------------------------------------------- |
| 日租金 ≤ 0     | `400 日租金不能低于 1 元`                                                                  |
| 日租金 > 99999 | `400 日租金不能高于 99999 元`                                                              |
| 押金 < 0      | `400 押金不能为负数`                                                                      |
| 正常          | `200 「京A·1644」已改价：日租金 ¥109.00 → ¥129.00，押金 ¥600.00 → ¥700.00。已成交订单按下单时的价格结算，不受影响。` |

对已租出的车也允许调价——订单在下单时已快照单价，改价只影响新订单。

### 4.2 状态变更

| 场景           | 返回                                              |
| ------------ | ----------------------------------------------- |
| 目标值不在 0/1/3  | `400 状态只能设置为 0 下架 / 1 可租 / 3 维保中；已租出由系统按订单自动维护` |
| `status = 9` | `400 状态取值只能是 0/1/3`                             |
| 目标等于当前       | `400 该车辆当前已是「可租」，无需重复设置`                        |
| 当前是已租出       | `400 该车辆当前为「已租出」，需先在订单里办理归还，才能调整状态`             |
| 正常           | `200 「京A·1644」状态：可租 → 维保中，该车已退出可租列表`            |

### 4.3 台账

| 场景                  | 返回                                             |
| ------------------- | ---------------------------------------------- |
| 内容少于 4 字            | `400 作业内容 4~500 字`                             |
| 类型非 MAINTAIN/REPAIR | `400 台账类型只能是 MAINTAIN（保养）或 REPAIR（维修）`         |
| 下次保养 ≤ 进场日期         | `400 下次保养日期必须晚于本次进场日期`                         |
| 正常（里程推进）            | `200 台账已登记（保养 · 2026-10-30），车辆里程已更新为 6.0 万公里。` |
| 正常（维修联动）            | `200 台账已登记（维修 · 2026-10-30），车辆已自动置为维保中，暂不可租。`  |

### 4.4 调车

| 场景        | 返回                               |
| --------- | -------------------------------- |
| 调入网点 = 自己 | `400 调入网点不能是本网点`                 |
| 调入网点不存在   | `404 调入网点不存在或已停用`                |
| 车辆不属于本网点  | `404 本网点不存在该车辆`                  |
| 车辆非可租     | `400 只有「可租」状态的车辆才能发起调车，当前状态：维保中` |
| 同车已有待审批   | `400 该车辆已有待审批的调车申请，请等待平台处理或先撤回`  |
| 重复撤回      | `400 该申请已处理（已撤回），无法撤回`           |
| 重复审批      | `400 该申请已处理（已通过），不能重复审批`         |
| 驳回不填原因    | `400 驳回必须填写原因，便于网点调整后再提`         |

## 7. 已知局限（如实记录）

1. **种子数据同车多单**：61 张未结束订单压在 24 台车上，`vehicle.status` 与订单状态  
   并不自洽。本轮把可用性判断统一到 `status` 规避了这个矛盾，但根治仍需重做 seed 排期。  
   影响：网点概览的「已租」数与订单量不呈 1:1。
2. **审批权只在平台**：网点之间不能直接协商调车。若答辩想演示「双方确认」，  
   需要另加一条网点同意环节，本轮按「资产归平台统一调度」建模。
3. **台账只增不改**：写错了只能补一条更正记录。对演示够用，对标的生产系统通常  
   还需要作废（保留痕迹）而不是物理删除。
4. **调车申请没有通知**：审批结果靠页面刷新查看，没有站内信/推送。
5. **价格变更无历史表**：改价直接覆盖 `vehicle.daily_price`，没有留痕。  
   订单侧有价格快照，所以历史订单不受影响，但「这台车上个月多少钱」查不到。

## 8. 三分钟演示脚本

1. `store1 / 123456` 登录 → 左侧「网点车辆」
2. 车 8 上点【台账】→ 抽屉里能看到 2026-04-25 的保养记录、下次保养 2026-10-25  
   → 列表里该车挂着橙色「该保养了（2026-10-25）」
3. 抽屉里登记一条维修台账（内容 ≥ 4 字）→ 提示「车辆已自动置为维保中」  
   → 关闭抽屉，该车状态已变「维保中」
4. 车 12 点【调价】→ 改成 159 / 800 → 提示改价成功
5. 「网点订单」→ 随便完成一单归还，回到车辆页看状态随之变化
6. 切到「调车申请」→ 选一台可租车 + 目标网点 → 提交 → 列表出现「待审批」
7. 换 `admin / 123456` → 「调车审批」→ 对该单点【通过】→ 提示归属迁移
8. 回到 `store1` 的车辆页 → 刚才那台车已不在列表（去了别的网点）
